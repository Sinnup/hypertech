# HT-010 — Slack-Initiated Pipeline

**Date:** 2026-06-17
**Status:** Completed
**Type:** Feature
**Branch:** `feat/HT-010-slack-pipeline`

## Summary

Add a `/new` Slack slash command that lets team members kick off a new pipeline run
(POC, internal, or production) directly from a Slack channel — no CLI access needed.

## Motivation

Currently, pipeline runs can only be started via `python main.py "prompt"` on the CLI.
For the CTO demo, Slack-initiated runs demonstrate how non-technical stakeholders
(product managers, compliance officers) can trigger the SDLC pipeline from their
normal workflow.

## Design

### New Slack command: `/new`

```
/new [--scenario <poc|internal|production>] <prompt>
```

**Examples:**
```
/new Quick POC: user profile page with avatar
/new --scenario production Build a payment KYC compliance screen
/new --scenario internal Analyze GDPR requirements for customer data storage
```

### Flow

```
Slack /new "prompt"
  → slack_commands.py validates + responds immediately with "queued" + ticket ID
  → background thread runs pipeline (orchestrator → scenario routing → agents)
  → on completion: Slack notification in #pipeline-alerts with ticket ID + status + URL
```

### Implementation

**File:** `core/notifications/slack_commands.py`

1. Add `_handle_new(text, user_id)` handler:
   - Parse `--scenario` flag (optional — orchestrator auto-detects if omitted)
   - Generate ticket ID (`HT-{random 6-char hex}`)
   - Register ticket in feature registry with status `queued`
   - Respond to Slack immediately: "🔄 Pipeline queued as `HT-XXXXXX` — will notify when done"
   - Spawn background thread running `main.py` pipeline
   - On pipeline completion, update registry and notify Slack

2. Register `/new` in the `slack_commands()` dispatch

**File:** `main.py` (minor)
- Consider extracting `run_pipeline(prompt, ticket_id, scenario)` as an importable function
  so slack_commands can call it without subprocess

### Slack UX

| State | Message |
|-------|---------|
| Queued | `🔄 Pipeline HT-XXXXXX queued — <scenario> path — will notify when complete` |
| Completed (POC) | `✅ HT-XXXXXX deployed at <url>` |
| Completed (Production) | `✅ HT-XXXXXX passed all gates — ready for review` |
| Failed | `❌ HT-XXXXXX failed at <agent> — check Langfuse trace` |

### Edge cases

- **Empty prompt**: Return usage help
- **Invalid scenario**: Return error with valid options
- **Pipeline crash**: Catch exception, update registry to `failed`, notify Slack
- **Duplicate detection**: Don't create duplicate tickets for identical prompts within 5 minutes

### Key design decisions

- **`run_pipeline()` extracted from `main()`** — Both CLI and Slack paths call the same function. CLI adds print + keepalive; Slack adds notification.
- **Immediate response** — Ticket ID generated and registry pre-populated before launching the background thread. Response returns in <10ms.
- **Async via `threading.Thread`** — Pipeline runs in a daemon thread. Flask returns immediately. On completion, Slack is notified via `slack.alert()`.
- **Scenario hint** — `--scenario` flag parsed from Slack text via regex. Passed through to registry pre-registration; orchestrator still does the real classification.
- **Graceful degradation** — If Slack webhook is unconfigured, `post()` returns `False` instead of crashing. Pipeline still runs.

### Edge cases handled

- Empty prompt → returns usage help
- Missing Slack config → pipeline runs, notifications silently skipped
- Pipeline exception → caught in `_run()`, registry updated to `failed`, Slack alerted
