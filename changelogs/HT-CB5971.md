# HT-CB5971 — coder_mobile generates a buildable Android project

- **Scenario**: fix
- **Agents**: coder_mobile
- **Branch**: feature/HT-CB5971 (stacked on feature/HT-728BAE)
- **Created**: 2026-06-25 21:10 UTC
- **Status**: in_progress

## Summary
A real `./gradlew assembleDebug` on a generated Android project failed twice:
1. `checkDebugAarMetadata` — AndroidX deps but no `gradle.properties`
   (`android.useAndroidX=true`).
2. `processDebugResources` — manifest referenced `@mipmap/ic_launcher` but the
   template generates no launcher-icon asset.

Because the project files come from the LLM (with a static fallback template),
the fix is a post-processing normalization applied to *every* generated file map.

## Changes
- **agents/coder_mobile/agent.py**: new `_ensure_buildable(file_map)`, applied
  after the file map is built (LLM or fallback). It (a) adds/patches
  `gradle.properties` to include `android.useAndroidX=true`, and (b) strips a
  dangling `@mipmap/ic_launcher` reference from the manifest when no icon asset
  is present. `import re` added.
- **tests/e2e/test_mobile_buildable.py** (new): 4 unit tests for the normalizer.

## Verification
- `uv run pytest tests/e2e/` → 23 passed.
- **Real APK build, no manual edits**: fresh `run_scenarios.py mobile` →
  project ships `gradle.properties` (useAndroidX) and no icon ref →
  `gradle assembleDebug` → `BUILD SUCCESSFUL`, real
  `app/build/outputs/apk/debug/app-debug.apk` (~8.4 MB, valid archive).

## Known limitation (backlog)
The generated `gradlew` is a stub and no `gradle-wrapper.jar` is shipped (a
binary can't live in a Python template). Building needs a local Gradle 8.2+
(`gradle assembleDebug`) or `gradle wrapper` first. Backlog: have infra generate
a real wrapper, or document the prerequisite in build instructions.
